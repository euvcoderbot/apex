# Azerbaijan qualifying loading correction — v135

The earlier v133 check covered pace summaries, not the qualifying telemetry path. The screenshot was reproduced on both the local and hosted `/api/session` endpoints: both returned HTTP 500 with `DataNotLoadedError`. The session response builder accessed `Session.session_info` even though that archive property had not loaded.

## Changes

- Check the loaded lap table inside the guarded retrieval block, whether or not a retained session already exists. An absent table enters the alternate source instead of escaping into later response construction.
- Read optional archive session metadata defensively. A missing metadata property no longer turns otherwise available observations into a server error.
- Adapt the validated OpenF1 bundle into the session shape used by qualifying consumers, including lap phases, sector times, tyre history, weather, status and identities. Preserve an explicit `openf1-session-start` clock label; these are not represented as F1 archive t0 timestamps.
- Retain the actual Azerbaijan qualifying session observations (22 drivers, 373 lap records), all 22 drivers' exact-fastest native car/position traces, and the sourced 20-corner Baku geometry. Existing session, individual telemetry and trace-batch recovery paths now consume those sources. Calculations are recomputed; no previous ranking or invented measurement is supplied.
- Captures are checksummed, exact-session/lap/time checked and expiring. Original timing capture controls the 30-day lifetime; repackaging does not renew it. Native capture checkpointing avoids repeatedly downloading successful laps during provider throttling. The MultiViewer geometry is its latest available Baku source year, 2022, not claimed to be a new 2026 survey.
- Source/backend hashes change, invalidating the previous derived request keys. The local Python process was restarted with the corrected code; a website reload is required to clear an already-rendered error held in browser memory.

## Verification

The same replay script runs through the local facade and the published dashboard facade, rather than testing only the backend summary. All requests below returned HTTP 200 without an error payload:

| --- | --- | --- |
| Session inventory | 22 drivers / 373 laps / 20 corners | same inventory |
| Exact-fastest trace batch | 11 requested / 11 received / 11 spatially measured | 22 requested / 22 received / 22 spatially measured |
| Qualifying corners | 11 requested / 11 received / 11 traces | 22 requested / 22 received / 22 traces |
| Straight-core measurement | 11 | 22 |
| Measured braking intervals | 80 | 153 |

Every captured native lap had full position coverage and a bounded start/finish timing window. The existing quality screen still leaves some individual corner windows unsupported; consequently the corner response's strict `complete` flag remains false. That is not a failed source request, and eligibility was not weakened to force it true. Native source downloads completed for every selected lap.

Browser verification on local compute: Azerbaijan alone, Qualifying, team Cornering, Straight line, Braking and driver Cornering. Driver Cornering rendered 22 rows; none of those category checks showed a `.performance-error`. The published facade replay separately exercised team and driver batches/corners against the deployed production backend.

228 JavaScript and 134 Python regression tests passed, including regressions for unavailable lap/session-info properties and Azerbaijan's full fastest-lap inventory. The production build passed. Replay evidence is generated by `scripts/verify-azerbaijan-loading.mjs`; source capture by `scripts/capture-azerbaijan-qualifying.py`.

This supersedes the earlier claim that successful pace-summary loading established that qualifying telemetry was working. Other events and every non-fastest lap were not exhaustively checked in this targeted correction.
